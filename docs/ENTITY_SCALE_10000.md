# 1万商品、24小时实体流程吞吐优化

目标：v4训练中实际出现的固定1万件商品，在24小时内完成分块、联合抽取、多轮补充、实体描述（保留独立审查）、消歧聚合五步。当前尚未证明目标已达成；语义图构建与推荐模型训练不在本次计时目标内。

## 已实施

- workflow_optimized.py：FIRST_COMPLETED有界队列，任务完成即补位；不再等待队首慢任务。工作流按完成顺序接收以立即记录进度，聚合前稳定排序。默认有序接口保留有界重排缓冲，避免无限预提交。
- 并发范围1..64。按实际服务吞吐选择，不能按并发数线性推算。
- 同一文本块多轮抽取、同一实体描述→审查仍按依赖顺序执行。
- 消歧/审查理由限制20个汉字或12个英文单词；实体、关系、证据ID和校验保留，没有跳过五步。此为提示词软约束，不截断原文证据。
- 成功缓存、逐商品products/*.json检查点、累计预算、重试和单商品失败隔离保留。构图可以独立关闭；extract_only状态明确列出剩余步骤，不能标为五步全部完成。
- 118项测试通过，包括慢队首补位、预算与token精确记账、缓存恢复、程序异常传播、抽取与完整流程状态区分等。

## 自动测速与生产门槛

入口：scripts/entities/run_scale.py
配置：configs/entity_workflow_10000_fast.yaml
执行：tmux会话ese-agp-entity-scale
记录：runs/entity_scale_10000_20261101/
启动日志：runs/entity_scale_optimization_20261101/launch.log

1. 固定哈希选择v4训练中实际出现的1万件商品，保存ID、数据指纹和文本SHA。
2. 在这些商品内按文本长度分层取64件，包含长文本，不挑最短商品。
3. 同一64件依次测试16/32/64并发联合抽取；出现明显错误或成功率不足时停止继续加压。
4. 选择成功商品吞吐最高的健康并发，同目录复用该标定的联合抽取缓存，执行剩余完整阶段。
5. 完整五步耗时=首次联合抽取标定耗时+后续续跑耗时。extraction_timing.json可能被续跑覆盖为缓存耗时，应该使用根status/report中phase_results保存的首次标定数据。
6. 以成功商品数估算1万件耗时，并加20%余量。如果不能落在剩余24小时内，标记needs_more_optimization，不启动预计无法按时完成的大任务。
7. 通过门槛才自动启动production完整五步；实际失败商品数如实保存，partial不视为全部成功。

24小时从标定开始计算，独立进程定时器及每请求剩余超时控制期限。未启动/未完成生产时，不能称已抽完1万件。
模型服务保持原样，不重启，不修改共享GPU服务。每线程独立HTTP适配器，应用缓存对各并发标定独立；模型已热且服务端前缀缓存未清理，比较不等于严格受控硬件实验。

## 分析边界

完整pilot的外推仍受候选规模、实体分布、长尾文本和共享服务负载影响，不是24小时承诺。每个请求的耗时在并发下重叠，不能相加作为墙钟时间。
最终生产报告和逐商品成功率才是是否达到目标的依据。候选策略和措辞优化的实体/合并质量还需抽样人工审查。
